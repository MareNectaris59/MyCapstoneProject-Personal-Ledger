## 二、为什么补单元测试

补之前 `backend/src/test/` 是**空目录** —— `pom.xml` 里有 `spring-boot-starter-test`，
但一个测试类都没有。全部验证靠端到端脚本（当时 322 项），代价是：

1. **改一行内核逻辑要跑一整套端到端**（起服务 + 连库 + 发上百个 HTTP 请求）才能发现问题；
2. **失败信息只告诉你「某个接口返回不对」**，不告诉你「哪条规则被破坏了」；
3. 边界条件（闰年、跨年周、舍入差额、窗口到期那一秒）在端到端里**很难穷举**。

## 三、为「可测性」做的三处改造

单元测试不是硬塞进去的 —— 有三处代码为了可测性做了调整，这本身就是设计改进。

### 3.1 把冲正逻辑抽成纯函数 `ReversalAllocator`

原本 `金额校验` 与 `反向分录按比例拆分` 是 `LedgerCoreService` 的**私有方法**。
它们不碰数据库，却只能靠起服务发 HTTP 才能验证。抽出后：

```java
// 校验并解析冲正金额（状态、是否可冲、金额上限）
public static BigDecimal resolveAmount(Ledger original, BigDecimal requested)

// 把冲正金额按比例拆分到各条原分录，末条承担舍入差额
public static List<Entry> allocate(Long reversalLedgerId, BigDecimal originalAmount,
                                   List<Entry> originalEntries, BigDecimal reversalAmount)
```

服务层只保留「取数据 + 事务 + 落库」。**改造后 322 项端到端全部通过**，确认没有改变外部行为。

### 3.2 给 `LoginAttemptGuard` 注入 `Clock`

限流器的核心行为是「窗口到期后解锁」。若直接依赖 `Instant.now()`，
测这一条就得真的等 10 分钟。改成构造时注入 `Clock` 后，测试可手动推进时间：

```java
clock.advance(Duration.ofSeconds(WINDOW_SECONDS - 1));  // 差一秒仍锁着
clock.advance(Duration.ofSeconds(1));                   // 正好到期即解锁
```

### 3.3 把「科目 + 对方账户」的校验从 CSV 导入里提出来复用

CSV 导入与定期记账都要判断"这对科目与交易类型是否匹配"。
若各写一份，两个入口迟早给出不同结论（用户会遇到"导入能过、定期记账不过"）。

现在两条路径共用同一套判断口径：支出配费用科目 + 资产账户、收入配收入科目
+ 资产账户、转账两端都是资产账户且不能相同。

## 五、单元测试真实发现的缺陷

### 5.1 `PeriodWindow.align` 边界判断错误（已修复）

| 项 | 内容 |
| --- | --- |
| 发现方式 | `PeriodWindowTest$Align.exactLengthIsAligned` |
| 位置 | `module/analysis/service/PeriodWindow.java` 的 `align` 方法 |
| 严重程度 | 中（不产生错误数据，但会给用户一条误导性提示） |

**背景**：统计未结束的周期（如 3 月过了一半）时，要把同比/环比的基期
裁剪成与「当前周期已过天数」等长，否则会得出「3 月只花了 2 月一半」的假象。

**缺陷**：判断写成了 `>=`：

```java
// 错误：基期长度「恰好等于」已过天数时，也被当成「基期不足」
if (elapsedDays >= baseLen) {
    return new Aligned(baseStart, baseEnd, false);   // aligned = false
}
```

当已过天数与基期长度**恰好相等**时（例如 2 月整月对上 28 天），
两段窗口本来就等长，属于「已经对齐」，却返回了 `aligned = false`。
前端据此显示「基期天数不足，按整段计算」，用户看到会以为数据有问题。

**修复**：

```java
// 正确：只有基期「真的比已过天数短」才算未对齐
if (elapsedDays > baseLen) {
    return new Aligned(baseStart, baseEnd, false);
}
```

**为什么端到端没发现**：这个分支只在「当前周期已过天数 ≥ 基期长度」时触发，
而端到端用例固定用 2026 年 9/10 月的数据，当天日期与基期长度不会恰好相等 ——
属于**必须靠穷举边界才能覆盖**的情形，正是单元测试的价值所在。

### 5.2 两处「写之前就想清楚」的缺陷（预防，非事后发现）

论文里值得单独说明的一点：有些缺陷是**通过穷举边界把它们在写代码时就排除掉**的，
而不是等它发生。

**其一：LIKE 通配符**。参数化查询只防 SQL 注入，不防 `%` 与 `_`。
若不处理，用户在搜索框输入一个 `%` 就会返回全部记录。
`SqlLike.escape` 与它的 8 项测试是在功能上线的同时就写好的。

**其二：定时任务重跑**。定时任务最典型的故障是"跑两次就多记一笔"。
幂等键 `rec-<规则ID>-<执行日>` 是确定性生成的，所以无论定时任务、
手动触发还是失败重试，同一期都只存在一条账目。
端到端里连续执行两次、以及"补跑 4 期后再执行一次"都断言新增为 0。

### 5.3 测试代码自身的一个坑（非产品缺陷，作为经验记录）

`LedgerStateTest` 用 `@CsvSource` 传入 `null` 时，JUnit 5 **默认不会**把字面量
`null` 转成 Java 的 `null`（默认 `nullValues` 为空），于是 `new BigDecimal("null")`
抛 `NumberFormatException`。已改为显式识别字符串 `"null"`。

记录这条是因为：**单元测试报错不一定是产品错了**，先分辨是产品缺陷还是测试写错。

## 六、覆盖范围与未覆盖部分

已覆盖（纯逻辑层）：

| 被测逻辑 | 关键边界 |
| --- | --- |
| 金额校验与运算 | 0.01 / 1000000.00 上下限、三位小数拒绝、`compareTo` vs `equals`、HALF_UP 舍入 |
| 账目状态机 | 差一分仍是 PARTIALLY、恰好冲完是 REVERSED、哪些状态可再冲正 |
| 预算周期窗口 | 周一/周日起始、跨年周归属、闰年与大小月、`next()` 连续性与跨年 |
| 分析时间窗口 | 自然日历对齐、环比跨年周回绕、同比按周序号对齐、`align` 三种边界 |
| 冲正分配 | 全额/部分冲正、舍入差额由末条补齐、拆分后借贷仍平衡、四条规则拒斥 |
| 登录限流 | 刚好 N 次/第 N+1 次、窗口差一秒与正好到期、邮箱与 IP 各自隔离、键归一化 |
| LIKE 转义 | `%` / `_` / 反斜杠的转义顺序、null 与纯空白、中文不受影响 |
| 定期记账日期 | 每周跨月跨年、闰日、锚定 31 与 29 的月末退让与恢复、到期与走完判定 |

**未覆盖**（刻意留给端到端）：

- 事务与回滚（需要真实数据库）
- 并发安全（100 线程并发记账，见端到端 AC-07）
- HTTP 契约、参数绑定、鉴权过滤器（需要 Spring 上下文）
- Mapper 里的 SQL 正确性（需要真实库）

也就是说：单元测试负责**规则与边界**，端到端负责**集成与契约**，两者互补而非替代。

## 七、论文可直接引用的表述

> 本项目为账务核心的纯逻辑层编写了 115 项 JUnit 单元测试，覆盖金额校验与运算、
> 账目状态机、预算周期窗口、分析时间窗口、冲正金额分配、登录失败限流、
> LIKE 通配符转义与定期记账日期推进八部分。
> 为使这些逻辑可被独立验证，将原属于 `LedgerCoreService` 私有方法的冲正校验与
> 反向分录拆分重构为无状态纯函数 `ReversalAllocator`，并为限流器引入可注入时钟。
> 测试全部通过，耗时约 0.54 秒，无需数据库或应用实例。
>
> 单元测试在实际开发中定位到一处边界缺陷：`PeriodWindow.align` 将「基期长度恰好
> 等于当前周期已过天数」误判为「基期不足」，导致前端显示误导性提示；该缺陷在固定
> 时间跨度的端到端用例中无法暴露，体现了边界穷举型单元测试的不可替代性。
> 单元测试与 377 项端到端测试互补：前者保证规则与边界的正确性，后者保证接口契约、
> 事务、并发与权限隔离的正确性。
