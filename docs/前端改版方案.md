## 一、精简：先砍掉"自证设计正确"的内容

### 1.1 问题定性

现在的界面有一类文案，是**写给我自己（和答辩老师）看的**，不是写给记账的人看的：

| 位置 | 现在的文案 | 问题 |
| --- | --- | --- |
| 分类与账户页 | 「这里是你的记账分类总表…这样做的好处是：每记一笔账，系统会同时记下…所以就算某一笔记错了、漏记了，你也能一眼看出来是哪一笔」 | 一整段**设计说明**。用户不需要被说服系统为什么这样设计 |
| 账目 → 详情 | 「一笔账会同时记在两个方面：钱从哪个账户出、归到哪一类消费。两边金额始终相等…」 | 同上，是**原理讲解** |
| 总览 → 账目检查 | 「这两项检查是系统自动完成的，用来保证你看到的余额准确无误。若出现异常，请先到「账目」页确认最近的记录。」 | 把一个内部自检机制暴露给用户 |

我数了一下，**用户可见的提示块共 10 处**（总览 4、账目 2、设置 2、登录 1、分类 1），另加 2 处字段提示。其中至少 5 处属于"解释系统为什么正确"，应当删除或压缩成一行。

**判断标准**（建议以后统一用这条）：文案只回答**"我该填什么"**和**"现在发生了什么"**。
凡是回答"系统为什么这么设计"的，删掉 —— 那是文档的职责，不是界面的。

### 1.2 逐页精简清单

| 页面 | 现状 | 改为 | 理由 |
| --- | --- | --- | --- |
| **分类与账户** | 独立页面（86 行），含科目树表格 + 6 列（编号/名称/类别/金额增加方向/能否记账/余额）+ 大段说明 | **整页删除** | 见 §1.3 |
| **总览** | 4 个统计卡（账户总余额/账户数量/账目核对/余额核对）+ 账户表 + 期初建账表单 + 账目检查卡片（4 个 alert） | 保留 2 个统计卡（总余额、本月支出）；账户表移到页面顶部并**支持新增账户**；期初建账收进账户行的下拉菜单；**删掉整个"账目检查"卡片** | 自检是内部机制，用户不需要看。真出问题时后端会报错，界面自然会提示 |
| **记一笔** | 转账下方的提示「转账只是在两个账户之间挪钱，不算消费，也不会影响预算」 | 压缩为「不算消费，不影响预算」 | 保留有用信息，去掉解释语气 |
| **账目** | 详情里的原理讲解 alert | **删除**，只留分录表格 | 用户点"详情"是想看这笔钱的去向，不是听课 |
| **账号设置** | 危险区的 4 条说明列表 | 压缩为 2 条 | 见 §3 |

### 1.3 「分类与账户」页为什么该删，功能往哪去

**核心判断：这一页是"科目表"的界面化，而"科目表"是复式记账的内部实现细节。**

用户的心智模型里没有"科目"这个概念。他有两个朴素需求：
1. 记一笔账 —— 需要**选一个分类**，偶尔需要**新建一个分类**
2. 看看钱在哪个账户 —— 需要**看到账户和余额**，偶尔需要**加一个账户**

现在这两件事被塞进一个要求理解"资产/费用/权益""金额增加方向""能否记账"的页面里。**功能是对的，位置是错的。**

改法（就地分散）：

| 原功能 | 新位置 | 交互 |
| --- | --- | --- |
| 查看账户与余额 | **总览**（页面顶部） | 已有账户表，位置不变 |
| 新增账户 | **总览** → 账户表右上角「+ 添加账户」 | 弹一个小表单：名称 + 类型（银行卡/微信/支付宝/现金/其他） |
| 设置期初余额 | **总览** → 账户行的「⋯」菜单 | 已有表单，改成弹出式 |
| 停用/删除账户 | **总览** → 账户行的「⋯」菜单 | 仅余额为 0 且无记录时允许删除，否则只能停用 |
| 查看分类 | **记一笔** → 分类下拉框 | 下拉框本身就是分类列表，不需要单独的页面 |
| 新增分类 | **记一笔** → 分类下拉框旁「+ 新建」 | 选中父分类时可建子分类；只暴露"名称"，隐藏编码/层级/方向 |
| 停用/删除分类 | **记一笔** → 下拉框内每项的「⋯」 | 已被使用过的分类只能停用（后端已有此约束，返回 1303） |

**保留但降级**：科目编码、类型、金额增加方向、层级 —— 这些在录入时**完全不显示**，由后端按规则生成（`subject_code` 已有自动生成逻辑，`normal_side` 由 `subject_type` 推导）。

**这一改的收益**：导航从 5 项降到 4 项（总览 / 记一笔 / 账目 / 账号设置），且**删除 86 行页面 + 一处需要用户理解会计概念的地方**。

### 1.4 精简后的信息架构

```
总览          余额 + 本月支出 + 账户列表（可增删改）+ 最近 5 笔
记一笔        支出 / 收入 / 转账（分类可就地新建）
账目          列表 + 详情 + 撤销
账号设置      账号信息 + 注销
```

侧边栏 4 项。没有"设置"之外的元信息页面。

## 二、风格改版：Brutalism → 轻量 Claymorphism

### 2.1 技能的原始输出

`--domain style "claymorphism soft 3d clay rounded"` 命中 `styles.csv` 的 Claymorphism 条目：

| 字段 | 技能返回值 |
| --- | --- |
| Keywords | Soft 3D, chunky, playful, toy-like, bubbly, thick borders, **double shadows**, rounded |
| Primary Colors | **Pastel: Soft Peach `#FDBCB4`, Baby Blue `#ADD8E6`, Mint `#98FF98`, Lilac `#E6E6FA`** |
| Effects | Inner+outer shadows (subtle, **no hard lines**), soft press (200ms ease-out), fluffy, smooth transitions |
| Border Radius | **16–24px**；Border Width 3–4px |
| Box Shadow | `inset -2px -2px 8px` + `4px 4px 8px` |
| Animation | soft bounce, `cubic-bezier(0.34, 1.56)` |
| Best For | Educational apps, children's apps, playful, onboarding, casual games |
| Complexity | Medium |

### 2.2 两处必须偏离技能的地方（需要你知情）

技能的输出是为"儿童应用 / 教育应用"设计的，直接用在记账软件上有两个实质问题：

**问题一：粉彩糖果色会削弱财务数据的可信度。**
`#FDBCB4`（蜜桃）/ `#98FF98`（薄荷）/ `#E6E6FA`（丁香紫）这套配色，加上 "Best For: children's apps" 的定位，会让"本月超支 1200 元"这类信息显得不严肃。

**处理**：按你选的"轻量 Claymorphism"，配色改用技能 `--domain color` 为
**Personal Finance Tracker** 命中的专业色板，只保留 Claymorphism 的**质感**（圆角、双层阴影、柔和过渡）：

| 令牌 | 值 | 来源 |
| --- | --- | --- |
| `--primary` | `#1E40AF` | 技能：Personal Finance Tracker Primary（trust blue） |
| `--accent` | `#059669` | 技能：同条目 Accent（profit green） |
| `--destructive` | `#DC2626` | 技能：同条目 Destructive |
| `--secondary` | `#3B82F6` | 技能：同条目 Secondary |
| 背景 | 浅色中性 `#F1F5F9` | **偏离**：技能给的是深色背景 `#0F172A`。记账软件用浅色更易长时间阅读，且与"柔和黏土"质感更搭 |
| 卡片 | `#FFFFFF` | 同上 |

**问题二：Claymorphism 的对比度风险是技能自己标注的 `conditional`。**
技能写明 Claymorphism 的 Accessibility 是 `risk:conditional`，要求 `contrast-text-4.5`。
而它的核心手法（柔和阴影、低对比描边）**天生降低对比度** —— 这是这个风格最大的落地风险。

**处理**：补查的能力确认了硬指标 ——
- 正文对比度 **≥ 4.5:1**，禁止"灰字灰底"（技能标记 Severity: High）
- 焦点指示器 **≥ 2 CSS px 周长、3:1 状态对比**，禁止细的低对比描边
- 因此**阴影只用于表达层次与可点击性，绝不承担信息区分职责**；借贷、收支、状态仍靠**颜色 + 文字**双重区分

### 2.3 风格令牌映射（Brutalism → Claymorphism）

| 令牌 | 现在（Brutalism） | 改为（Claymorphism） |
| --- | --- | --- |
| `--radius` | `0` | `20px`（技能值 16–24，取中） |
| `--border-width` | `3px` 纯黑实线 | `1px` 极浅描边 `rgba(15,23,42,0.06)`（技能说 3–4px 厚边框，但那是为"玩具感"服务的，与轻量化目标冲突，故减薄） |
| 阴影 | `4px 4px 0 #000`（硬偏移） | `--shadow-outer: 6px 6px 16px rgba(15,23,42,0.10)` + `--shadow-inner: inset -2px -2px 6px rgba(255,255,255,0.9)` |
| 按下反馈 | `translate(4px,4px)` + 阴影归零 | `translateY(1px)` + 外阴影收缩，`200ms cubic-bezier(0.34,1.56)`（技能的 soft bounce） |
| 字体 | Fira Code + Fira Sans | **不变**（技能的 "Dashboard Data" 搭配本就是为数据面板选的，换成 Claymorphism 不影响这个判断） |
| 全站 0 圆角 | 是 | **改为全站 20px**，仅进度条/表格行保持一致 |

### 2.4 需要重新审视的组件

改风格时这几个组件的现设计**必须重做**，因为它们的视觉逻辑建立在"硬边框"上：

| 组件 | Brutalism 依赖 | Claymorphism 改法 |
| --- | --- | --- |
| **天平式分录预览** | 左右等宽 + 中间 3px 黑竖线 + 整块黄底 | 改为**左右两张浮起的黏土卡片**，中间留白而非硬线；平衡时两张卡都有绿色内发光，不平衡时红色。**"平衡可感知"这个设计意图保留** |
| 表格 | 2px 黑线分隔行 | 去掉行线，改用斑马纹 + 悬浮时整行浮起（阴影） |
| 状态标签 | 实心色块 + 2px 黑边 | 改为**浅色底 + 深色字 + 20px 圆角胶囊**，无边框 |
| 按钮 | 硬阴影 + 按下位移 | 双层阴影 + 按下缩进，无边框 |
| Toast | 顶部整条横幅 | 改为**右下角浮起的黏土胶囊**，因为横幅式提示与柔和风格冲突 |

## 三、注销确认改造

### 3.1 现在的问题

```
请输入「注销账号」以确认
[                    ]
```

这个模式（GitHub 用仓库名、Vercel 用项目名）的适用场景是**批量操作或不可逆的破坏性操作**。
用在"注销自己的账号"上确实别扭 —— 用户会想"我当然知道我要注销，为什么还要我抄四个字"。

### 3.2 改为输入注册邮箱

```
注销账号会删除你的账号，这不是退出登录。
账号立即失效、无法再登录，也无法找回。
昵称、头像、邮箱等个人信息会被清除。
你的账务记录会被保留但无法再访问。

请输入你的注册邮箱以确认：          ← 新增说明
[  you@example.com                ]

登录密码
[  ••••••••                       ]

注销原因（选填）
[                                 ]

[ 确认注销账号 ]  [ 取消 ]
```

**为什么是邮箱而不是昵称**：
- 邮箱是账号的**唯一标识**，与登录方式一致，用户一定记得
- 昵称可重复、可修改，作为确认凭据强度不足
- 后端已有邮箱登录逻辑，前端拿到 `auth.user.email` 即可本地比对

**交互细节**：

| 项 | 设计 |
| --- | --- |
| 比对方式 | 前端**不区分大小写**比对 `auth.user.email`（后端无需新增校验，邮箱本来就不该出现在请求里） |
| 按钮启用条件 | 邮箱匹配 **且** 密码非空 |
| 不匹配时的反馈 | 输入框下方即时提示「与注册邮箱不一致」，**不等用户点按钮** |
| 密码是否保留 | **保留**。邮箱证明"你是这个账号的主人"，密码证明"你是本人"，两者职责不同 |
| 后端改动 | **零改动**。`DeleteAccountRequest` 仍只需要 `password` 和 `reason` |

### 3.3 说明文字的改动

| 现在 | 改为 |
| --- | --- |
| 4 条 bullet 列表 | 压缩为 3 句短句（见上图），去掉"该邮箱之后可以重新注册一个全新账号，但旧数据不会恢复"这句 —— 它是实现细节，且会诱导用户尝试 |

## 四、需要你确认的取舍

### 4.1 一个我认为有风险的点

**删掉「账目检查」卡片后，系统的自检结果就没有界面入口了。**

那个卡片展示的是"借贷是否平衡""账户余额与流水是否一致"—— 它是这个系统**最核心的工程价值**（复式记账相对单式记账的全部意义就在于此），但在答辩时如果界面上完全看不到，评审可能认为"看不到你所谓的一致性保证"。

三个选项：

| 方案 | 说明 |
| --- | --- |
| **A. 彻底删掉** | 最精简。自检仍在后端每日跑，只是不展示 |
| **B. 收进「账号设置」页的一个折叠区** | 日常不打扰，需要时（或答辩演示时）能展开 |
| **C. 只保留一行状态** | 总览底部一行小字：「✓ 账目核对正常」/「✗ 发现异常」，点击才展开细节 |

我倾向 **C**：占一行、不解释、异常时才醒目。既不干扰日常使用，也保住了这个能力的可见性。

### 4.2 关于"小而美"的一个建议

除了删页面，还有一件事值得做：**总览页加"本月支出"和"最近 5 笔"**。

现在总览只有余额和对账，**用户打开应用最想知道的"我这个月花了多少"却要跳到账目页去查**。
这比删掉分类页对"好用"的提升更大。建议一并做进去（数据可从已有的
`GET /api/v1/ledgers/summary` 或 `GET /api/v1/ledgers` 取，无需新增接口）。
